# 322. Coin Change

## Problem (LeetCode Statement)

**Input:**
- `int[] coins` — array of distinct coin denominations
- `int amount` — target amount to make

**Output:**
- Fewest number of coins needed to make up `amount`, or `-1` if impossible

**Task:**
Given infinite supply of each coin, find the minimum number of coins that sum to `amount`.

---

## Constraints

- `1 <= coins.length <= 12`
- `1 <= coins[i] <= 2^31 - 1`
- `0 <= amount <= 10^4`
- Answer can never exceed `amount` coins (worst case: all 1-value coins)

---

## Examples
```
Input:  coins = [1, 5, 11], amount = 15
Output: 3  (5 + 5 + 5)
```
```
Input:  coins = [1, 5, 11], amount = 11
Output: 1  (11)
```
```
Input:  coins = [2], amount = 3
Output: -1
```

---

## What Actually Matters

- Order of coins doesn't matter — you're minimizing count, not tracking which coins
- You have infinite supply — the same coin can be reused any number of times
- Brute force (try all combinations) explodes exponentially — overlapping subproblems make it a DP candidate
- The answer for `amount` depends entirely on answers for smaller amounts — classic optimal substructure

---

## Core Insight

> For every amount `i`, try every coin — if you can reach `i - coin`, then `dp[i - coin] + 1` is a candidate answer. Take the minimum across all coins.

---

## Invariant / Mental Model

> When computing `dp[i]`, every `dp[j]` where `j < i` is already finalized. The loop order guarantees this — you never need a value you haven't computed yet.

---

## Thinking Log (Evolution of the Solution)

- **Initial Thought:** If we need the solution for amount 11, we need it for 10, then 9 — this feels top-down, recursive
- **Issue:** Recursion without memoization recomputes the same subproblems repeatedly
- **Correction:** Bottom-up builds from amount 0 upward — by the time we reach `i`, all smaller answers are ready in the table. No recursion needed
- **Confusion:** Thought DP required recursion — assumed bottom-up must also recurse somewhere
- **Clarification:** Recursion is only one *mechanism* for DP (top-down). Bottom-up uses a loop instead. Both avoid recomputation — just in opposite directions
- **Final Realization:** Define `dp[i]` = min coins for amount `i`. Fill from 0 to amount. At each step, try every coin and take the minimum. The loop *is* the DP.

---

## Algorithm (High Level)

1. Create `dp` array of size `amount + 1`, fill with `amount + 1` (acts as infinity — larger than any valid answer)
2. Set `dp[0] = 0` (base case — zero coins needed for amount zero)
3. For every amount `i` from 1 to `amount`, try every coin — if `coin <= i`, update `dp[i] = min(dp[i], dp[i - coin] + 1)`
4. After the loop, if `dp[amount]` is still greater than `amount`, it was never reached — return `-1`. Otherwise return `dp[amount]`

---

## Code (Reference Only)
```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int[] dp = new int[amount + 1];
        Arrays.fill(dp, amount + 1);
        dp[0] = 0;

        for (int i = 1; i <= amount; i++) {
            for (int coin : coins) {
                if (coin <= i) {
                    dp[i] = Math.min(dp[i], dp[i - coin] + 1);
                }
            }
        }
        return dp[amount] > amount ? -1 : dp[amount];
    }
}
```

---

## Edge Cases to Recall

- `amount = 0` → always return 0, handled by `dp[0] = 0`
- No combination reaches `amount` → `dp[amount]` stays at `amount + 1` → return `-1`
- Don't use `-1` as the infinity sentinel — `min()` would pick it over valid answers and corrupt the table

---

## One-Line Recall

> Fill `dp[0..amount]` with infinity except `dp[0]=0`, then for each amount try every coin and take `min(dp[i], dp[i-coin]+1)`, return `-1` if unreached.
