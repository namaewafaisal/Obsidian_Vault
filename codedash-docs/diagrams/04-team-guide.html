Git workflow

Branch strategy:
main ← protected, production-ready only
dev ← integration branch, all PRs merge here first
feature/* ← individual feature branches

Example branches:
feature/sync-engine-core
feature/leetcode-adapter
feature/leaderboard-ui

Commit convention:
feat: add BullMQ queue setup for leetcode sync
fix: handle null rating in codeforces adapter
chore: add docker-compose for local dev
docs: update DEPLOY.md with Atlas setup steps

Rules that keep teams from falling apart

No one is "just the frontend person." Every person owns a backend component too. If someone only writes React, they have nothing interesting to say in a backend interview — and this project's value is in the backend.
Agree on API contracts early. Before building adapters, agree on the shape of what each adapter returns and what the queue job object looks like. Write this in a CONTRACTS.md file. Person 2 and Person 3 both feed into Person 1's queue — they need to agree on the job schema first.
GitHub Issues for every task. Every feature is an issue, assigned to an owner, with a rough due date. No ambiguity about who is doing what.
Don't go 3+ days without a commit if you're supposed to be building. A dead repo is a red flag in interviews. Keep the contribution graph green.
Don't rescue teammates silently. If you do someone else's feature because they're stuck, note it in the PR description. You get the credit for the commit, not them.
PR rule: Every PR to dev needs 1 review. Person 1 (Mohamed) does final merge to main. This is already set up via GitHub branch rulesets — you know how to do this from the OTT project.
