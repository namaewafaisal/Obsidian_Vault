Two Views, Two Query Patterns

The leaderboard never touches platform_data. The detail page never re-runs a filter query. Clean separation.

View 1 — Leaderboard / dashboard
Filter year, platform, min solved. Sort by hard/medium/rating.
1
Faculty selects: Year 3 / LeetCode / min 200 solved / sort by hard
2
API checks Redis cache — key is hash of query params. Cache HIT = instant response.
3
Cache MISS — query students collection only. Compound index makes this ~5ms.
4
Store result in Redis with 1hr TTL. Return to client.
5
Faculty switches to Codeforces view — client-side re-sort of already-fetched data. Zero new DB query.
Student.find({
  year: 3,
  "lc.solved": { $gte: 200 }
}).sort({ "lc.hard": -1 })
.select("name roll lc cf cc")
.limit(100)
// hits: { year:1, "lc.solved":-1 } index
View 2 — Student detail page
Click any row in the leaderboard to open a student's full profile.
1
User clicks student row. Browser requests /api/students/:id/detail
2
Two parallel DB queries fire simultaneously (Promise.all)
3
students.findById — returns basic info + summary stats (already have these from leaderboard, but confirming freshness)
4
platform_data.find({student_id}) — returns at most 5 docs (one per platform). Full submissions, topic tags, contest history.
5
Merge and return. Stale platforms (last_synced > 3 days) get a warning badge in the UI.
const [student, platforms] =
  await Promise.all([
    Student.findById(id),
    PlatformData.find(
      { student_id: id }
    ) // max 5 docs total
  ])

Platform switching on the leaderboard — no extra query

When faculty switches from "LeetCode" to "Codeforces" view, you do NOT re-query the DB. All summary numbers (lc.*, cf.*, cc.*) are already embedded in the same student documents that were fetched for the initial leaderboard. The frontend re-sorts the existing data by cf.rating instead of lc.hard. This is either a client-side sort (instant) or a new API call to the same endpoint with a different sort key (fast, often cached).
Stale data — never show zeros. If a platform sync failed, show the last known value with a "last updated X days ago" badge. Empty cells are confusing — was the score 0 or did the sync fail? Always show something with context. The lc.sync_status and lc.last_synced fields in the student document are exactly for this.
