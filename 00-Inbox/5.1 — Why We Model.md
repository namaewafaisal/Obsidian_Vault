# 5.1 — Why We Model

A model:
> a simplified representation of a real system created for a specific purpose.

Models help developers:
- visualize systems
- communicate ideas
- reduce complexity
- plan before coding

---

# Why Modelling Is Needed

Large systems become difficult to understand directly from code.

Without models:
- communication problems occur
- architecture becomes unclear
- integration becomes harder
- system complexity increases

---

# Real World Analogy

Before building a house:
- architects create blueprints.

Before building software:
- developers create models/diagrams.

---

# Important Insight

A model is NOT the real system.

A model:
- hides unnecessary details
- focuses only on important concepts

This simplification is called:
> abstraction

---

# UML (Unified Modeling Language)

UML:
> standardized language for software diagrams.

Purpose:
- common notation
- consistent communication
- understandable diagrams across teams

---

# Why UML Exists

Without UML:
- every company/team may draw diagrams differently.

UML standardizes:
- symbols
- relationships
- structure

---

# UML Diagram Categories

## 1. Structural Diagrams

Describe:
> what exists in the system.

Focus:
- classes
- objects
- relationships
- architecture

---

## Examples
- Class Diagram
- Use Case Diagram

---

# 2. Behavioural Diagrams

Describe:
> how the system behaves.

Focus:
- workflows
- interactions
- state changes

---

## Examples
- Sequence Diagram
- Activity Diagram
- State Diagram

---

# Structural vs Behavioural

| Structural | Behavioural |
|---|---|
| Static view | Dynamic view |
| What exists | What happens |
| Relationships | Interactions/workflows |

---

# Example Workflow

Requirements
→ Use Case Diagram
→ Class Diagram
→ Sequence Diagram
→ Implementation

Different diagrams represent different perspectives of the system.

---

# Why Modelling Before Coding Helps

Modelling helps:
- detect design issues early
- improve architecture clarity
- organize responsibilities
- simplify communication

Without modelling:
- systems may become poorly structured

---

# Abstraction in Modelling

Models intentionally omit implementation details.

Example:
A class diagram shows:
- classes
- attributes
- relationships

It does NOT show:
- full Java code
- SQL queries
- implementation logic

---

# Commonly Used Diagrams

Most practical diagrams:
- Use Case Diagram
- Class Diagram
- Sequence Diagram
- Activity Diagram

---

# Important Insight

Different diagrams answer different questions:

| Diagram | Main Purpose |
|---|---|
| Use Case | User interaction |
| Class Diagram | System structure |
| Sequence Diagram | Object interaction over time |
| Activity Diagram | Workflow/process flow |

---

# Real Industry Relevance

Modern teams may use:
- lightweight UML
- whiteboard sketches
- architecture diagrams

Formal UML documents are less common,
but modelling itself is still heavily used.

---

# Key Idea

Modelling improves:
- understanding
- communication
- planning
- maintainability

before implementation begins.
