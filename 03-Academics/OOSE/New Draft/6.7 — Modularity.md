# 6.7 — Modularity

Modularity:
> dividing a system into smaller independent modules.

Each module should:
- handle a specific responsibility
- interact through clear interfaces
- remain as independent as possible

---

# Example

```text
ECommerce System
├── Auth Module
├── Product Module
├── Cart Module
├── Payment Module
└── Notification Module
```

Each module handles:
> one concern/responsibility

---

# Benefits of Modularity

- easier maintenance
- easier debugging
- parallel development
- code reuse
- independent testing
- better scalability

---

# Characteristics of Good Modules

- high cohesion
- low coupling
- clear interfaces
- single responsibility

---

# Module Interface

Defines:
> how other modules interact with the module

Example:

```java
PaymentService.processPayment()
```

Internal implementation remains hidden.

---

# Information Hiding

Expose:
- necessary operations only

Hide:
- internal logic
- internal data

Example:

```java
public void login()
```

Internal methods hidden:

```java
private validatePassword()
private generateJWT()
```

---

# Poor Modular Design

```text
Huge UserService
- login
- payment
- email
- analytics
```

Mixed responsibilities.

---

# Good Modular Design

```text
AuthService
PaymentService
NotificationService
AnalyticsService
```

Responsibilities separated properly.

---

# Modularity vs Cohesion vs Coupling

| Concept | Focus |
|---|---|
| Cohesion | Internal module quality |
| Coupling | Dependency between modules |
| Modularity | Overall system decomposition |

---

# Important Insight

Modularity reduces:
> ripple effect

Changes in one module should minimally affect others.

Good modularity improves:
- maintainability
- scalability
- team productivity
