# 4.3 — Software Requirement Specification (SRS)

## Definition

SRS:
> a formal document describing what the software system should do.

Acts as:
- agreement between customer and developers
- reference for development
- reference for testing
- reference for maintenance

---

# Why SRS Is Needed

Without SRS:
- requirements become unclear
- misunderstandings happen
- scope changes uncontrollably
- testing becomes difficult

SRS provides:
> a single source of truth.

---

# IEEE 830 SRS Structure

1. Introduction
2. Overall Description
3. Specific Requirements
4. Appendices

---

# 1. Introduction

## Purpose
Explains:
- why the system exists
- what the document is about

## Includes
- purpose
- scope
- definitions
- references
- overview

---

## Example

### Purpose
```text
This system manages online course enrollment for students.
```

### Scope
```text
The system allows students to register, enroll in courses, and view grades.
```

---

## Why Needed

Helps readers quickly understand:
- project goal
- system boundaries
- terminology

Without this:
- confusion about project scope occurs.

---

# 2. Overall Description

## Purpose
High-level overview of the system.

Describes:
- environment
- users
- constraints
- major features

---

## Includes

### Product Perspective
Where system fits.

Example:
```text
The application integrates with the college ERP system.
```

---

### Product Functions
Major system capabilities.

Example:
- login
- enrollment
- payment
- report generation

---

### User Classes
Types of users.

Example:
- students
- admins
- faculty

---

### Constraints
System limitations.

Example:
```text
System must run on Linux servers.
```

---

### Operating Environment
Where software runs.

Example:
```text
Backend: Linux
Database: PostgreSQL
Frontend: Web browser
```

---

## Why Needed

Gives developers:
- system context
- environment understanding
- technical boundaries

Without this:
- wrong assumptions happen.

---

# 3. Specific Requirements

## Purpose
Most detailed and important section.

Defines exact system behaviour.

---

# Functional Requirements

Define:
> what the system shall do.

---

## Example

```text
System shall allow students to enroll in available courses.
```

```text
System shall send email verification during registration.
```

---

# Non-Functional Requirements

Define:
> how the system behaves.

---

## Performance Example

```text
System shall respond within 2 seconds.
```

---

## Security Example

```text
Passwords shall be stored using hashing.
```

---

## Reliability Example

```text
System shall maintain 99.9% uptime.
```

---

# Interface Requirements

Define interactions with:
- users
- hardware
- software
- APIs

---

## Example

```text
System shall integrate with Razorpay payment API.
```

---

## Why Specific Requirements Matter

This section becomes the base for:
- coding
- testing
- validation

Test cases are usually written directly from these requirements.

---

# 4. Appendices

## Purpose
Store extra supporting information.

---

## Examples
- diagrams
- references
- glossary
- database schema

---

## Why Needed

Keeps main SRS clean while preserving useful technical details.

---

# Writing Good Requirement Statements

---

# Bad Requirement

```text
System should be fast.
```

Problems:
- vague
- not measurable
- not testable

---

# Good Requirement

```text
System shall respond to search requests within 2 seconds.
```

Now:
- measurable
- testable
- clear

---

# “Shall” vs “Should”

| Word | Meaning |
|---|---|
| Shall | Mandatory |
| Should | Optional/recommended |

---

# Example

## Strong Requirement
```text
System shall encrypt user passwords.
```

Mandatory.

---

## Weak Requirement
```text
System should encrypt user passwords.
```

Sounds optional.

---

# Characteristics of Good SRS

---

## Complete
No important requirement missing.

---

## Consistent
Requirements do not conflict.

### Bad Example
```text
System supports offline mode.
```

```text
System requires internet connection always.
```

Conflict exists.

---

## Unambiguous
Only one interpretation possible.

### Bad Example
```text
System should load quickly.
```

“Quickly” is unclear.

---

## Verifiable
Requirement can be tested.

### Example
```text
System shall support 1000 concurrent users.
```

Can be measured.

---

## Traceable
Requirement can be tracked through:
- design
- code
- testing

---

## Modifiable
Easy to update when requirements change.

---

# Functional vs Non-Functional

| Functional | Non-Functional |
|---|---|
| What system does | How system behaves |
| Login | Performance |
| Payment | Security |
| Report generation | Reliability |

---

# Important Insight

Bad SRS creates:
- wrong implementation
- testing confusion
- project delays
- maintenance problems

A well-written SRS reduces:
- ambiguity
- rework
- communication issues

---

# Real Industry Relevance

Even Agile teams still write:
- tickets
- acceptance criteria
- API contracts
- feature specifications

Modern systems may use lighter documentation,
but clear requirements are still essential.
