# PART 1 — The Foundation: Why Does Software Engineering Exist?

## 1.1 — What Even Is Software Engineering?
- The difference between *writing code* and *engineering software*
- Why building a to-do app and building a hospital management system are categorically different problems
- The NATO 1968 conference: where the term was coined and why there was a "software crisis"
- The core claim of SE: **software can be built systematically, predictably, and at scale**
- Sommerville's definition vs Pressman's definition (and why both exist)
- What a Software Engineer actually does day-to-day vs what a programmer does

## 1.2 — The Four Core Activities (What SE Is Made Of)
- **Specification** — figuring out what to build (not the same as requirements gathering)
- **Design** — deciding how to build it before writing a line of code
- **Validation** — proving it does what it's supposed to
- **Evolution** — changing it after it's deployed (the activity that never ends)
- Why these four activities exist in every model, even when they're not called by these names
- The cost of change curve: fixing a bug in production costs 100x what fixing it in design costs

## 1.3 — What Is a Software Process?
- Process vs methodology vs framework — why people confuse these terms
- A process is a sequence of activities that produces a software product
- Why you need a process at all: without one, you get chaos, missed deadlines, and software nobody can maintain
- The input-output chain: requirements → design artifacts → code → tested system → deployed product
- What "process model" means: a simplified description of a software process, presented from a particular perspective

# PART 2 — Process Models: How Do You Organize Building Software?

## 2.1 — The Waterfall Model
- The story of why Waterfall was invented (came from manufacturing and construction)
- The phases in order: Requirements → System Design → Implementation → Testing → Deployment → Maintenance
- The key constraint: each phase must be complete before the next begins
- **Advantages**: simple to manage, clear milestones, documentation-heavy (good for regulated industries)
- **Disadvantages**: inflexible to change, customer sees nothing until very late, testing happens too late to fix fundamental problems
- When Waterfall is actually the right choice (defense, aerospace, medical devices)
- Why Waterfall fails for most modern software: requirements change, customers don't know what they want upfront

## 2.2 — The Incremental Model
- The insight: instead of one big delivery, deliver in slices
- How it works: requirements → design → implement → deliver Increment 1, then loop
- The difference between increment (adds new functionality) and iteration (refines existing functionality)
- **Advantages**: customer gets working software early, risk is distributed across increments, feedback is faster
- **Disadvantages**: overall system architecture can degrade across increments if not managed, hard to define clean increments upfront
- Real-world example: building a browser — first increment is basic page rendering, second is tabs, third is bookmarks

## 2.3 — RAD (Rapid Application Development)
- The motivation: compress the development timeline by parallelising activities
- Key idea: use component reuse, prototyping, and RAD tools to build fast
- The 60-90 day delivery promise and why it requires experienced teams
- **Advantages**: very fast delivery, heavy customer involvement, good for well-scoped projects
- **Disadvantages**: requires large team for parallelism, not suitable for technically complex systems, can produce technically poor but fast code
- Why RAD matters today: it's the ancestor of modern low-code/no-code thinking

## 2.4 — Specialized Process Models
- **Component-Based Software Engineering (CBSE)**: build software by assembling pre-built components; what a component is (reusable, independently deployable, with a defined interface); how this relates to npm packages, Maven dependencies, microservices
- **Formal Methods**: using mathematical specification to prove software correctness; Z notation basics; why this is used in safety-critical systems (aircraft, medical); why it's not mainstream (expensive, requires mathematicians)
- **Aspect-Oriented Development**: separating cross-cutting concerns (logging, security, transactions) from core logic; why this exists; how it shows up in real frameworks (Spring AOP)

## 2.5 — Comparing the Process Models [TABLE]
- Side-by-side comparison: flexibility, customer visibility, risk profile, documentation, team size requirements
- How to answer a "compare Waterfall and Incremental" exam question without just listing definitions
- The underlying question all models are trying to answer: *how do you manage change and uncertainty?*

# PART 3 — Agile: The Paradigm Shift

## 3.1 — Why Agile Exists (The Problem With Plan-Driven Development)
- The story of software projects failing not because programmers were bad, but because requirements changed
- The cost of change problem in Waterfall: change is expensive because everything downstream must be redone
- The insight behind Agile: *embrace change* instead of trying to eliminate it
- The Chaos Report context: in the 1990s, the majority of software projects failed or were over-budget

## 3.2 — The Agile Manifesto
- The four values (not just memorisation — understand what each is reacting against):
  - Individuals and interactions **over** processes and tools
  - Working software **over** comprehensive documentation
  - Customer collaboration **over** contract negotiation
  - Responding to change **over** following a plan
- Why the right-hand side still matters ("there is value in the items on the right")
- The 12 principles: grouped by theme (delivery, customer, technical excellence, team, sustainability)
- What Agile is NOT: not "no planning", not "no documentation", not "chaos"

## 3.3 — Extreme Programming (XP)
- XP's context: small teams, high-change environments, technically demanding projects
- The five XP values: Communication, Simplicity, Feedback, Courage, Respect
- Core XP practices explained mechanically (not just named):
  - **Planning Game**: write user stories, estimate them, commit to an iteration
  - **Small Releases**: working software every 1-2 weeks
  - **Metaphor**: shared vocabulary for the system architecture
  - **Simple Design**: don't build what you don't need now (YAGNI — You Aren't Gonna Need It)
  - **Test-Driven Development (TDD)**: write the failing test first → write code to pass it → refactor; the red-green-refactor cycle in detail
  - **Refactoring**: continuously improve code structure without changing behaviour
  - **Pair Programming**: two developers, one keyboard; driver writes code, navigator reviews in real-time
  - **Collective Code Ownership**: anyone can change any code at any time
  - **Continuous Integration (CI)**: integrate to the shared repo multiple times per day, automated build runs immediately
  - **Sustainable Pace**: no death marches; 40-hour weeks
  - **On-Site Customer**: a real customer representative is part of the team
  - **Coding Standards**: agreed conventions so collective ownership is practical

## 3.4 — The XP Process Flow [DIAGRAM]
- Drawing the XP loop: User Stories → Release Planning → Iteration Planning → Coding + Testing → Small Release → Customer Feedback → back to top
- User story format: "As a [role], I want [feature] so that [benefit]" — and why this format exists (it keeps focus on value, not features)
- Iteration = 1-2 week cycle; Release = collection of iterations

## 3.5 — Scrum (As Context for Comparison)
- Scrum is a framework, XP is a set of engineering practices — they complement each other
- Scrum roles: Product Owner, Scrum Master, Development Team
- Scrum artifacts: Product Backlog, Sprint Backlog, Increment
- Scrum events: Sprint Planning, Daily Standup, Sprint Review, Sprint Retrospective
- Sprint = 2-4 week iteration
- Velocity: how much work a team completes per sprint (used for planning)
- **Key exam trap**: Scrum does not prescribe engineering practices (no TDD, no pair programming); XP does

# PART 4 — Requirements: Figuring Out What to Build

## 4.1 — Requirements Engineering Overview
- The difference between a need, a requirement, and a specification
- Why requirements are the hardest part of software development (the customer problem)
- Functional requirements: what the system shall do ("The system shall allow users to reset their password")
- Non-functional requirements: how the system shall perform — categories: performance, security, reliability, usability, maintainability, portability
- The properties of a good requirement: complete, consistent, unambiguous, verifiable, traceable, feasible

## 4.2 — Requirements Elicitation Techniques
- **Interviews**: structured vs unstructured; what questions to ask; what customers say vs what they mean
- **Observation (Ethnography)**: watch users work; surfaces implicit requirements they can't articulate
- **Prototyping**: build a throwaway UI to get feedback; evolutionary vs throwaway prototypes
- **Joint Application Development (JAD)**: structured workshop with all stakeholders; surfaces conflicts early
- **Questionnaires**: good for large user populations; bad for nuanced understanding
- When to use which technique

## 4.3 — Software Requirement Specification (SRS) [IEEE 830]
- Why SRS exists: shared contract between customer and development team
- IEEE 830 structure section by section:
  1. Introduction (Purpose, Scope, Definitions, References, Overview)
  2. Overall Description (Product Perspective, Functions, User Classes, Operating Environment, Constraints)
  3. Specific Requirements (Functional, Non-functional, External Interface)
  4. Appendices
- How to write a well-formed requirement statement: use "shall" not "should"; one requirement per statement; measurable; avoid ambiguous words ("fast", "user-friendly", "easy")
- Mini-SRS writing exercise: write three functional and two non-functional requirements for a library management system

# PART 5 — Modelling: Communicating Design With Diagrams

## 5.1 — Why We Model (Before Any Specific Diagram)
- A model is a simplified representation of reality, built for a specific purpose
- The purpose of UML: a standard language so diagrams mean the same thing to everyone
- UML diagram categories: Structural (what exists) vs Behavioural (what happens)
- You don't need all 14 diagram types — exam needs 5-6; career needs the same 5-6

## 5.2 — Use Case Diagrams [STRUCTURAL/BEHAVIOURAL]
- What a use case represents: a goal a user has, fulfilled by the system
- Actors: primary (initiates the use case), secondary (participates but doesn't initiate)
- System boundary box: what's inside the system vs what's outside
- Relationships:
  - Association: actor uses a use case (simple line)
  - `<<include>>`: use case A always includes use case B as a mandatory sub-step
  - `<<extend>>`: use case B optionally extends use case A under a condition
  - Generalisation: one actor or use case is a specialisation of another
- **The include vs extend trap question**: include = mandatory, always happens; extend = optional, conditional
- Use case description template: Name, Actor, Preconditions, Main Success Scenario (numbered steps), Alternate Flows, Exception Flows, Postconditions
- Drawing exercise: ATM system use case diagram

## 5.3 — Class Diagrams [STRUCTURAL]
- OOP prerequisite: class vs object, attribute vs method, encapsulation, inheritance, polymorphism
- Class box anatomy: class name (top), attributes (middle), methods (bottom)
- Visibility notation: + public, - private, # protected, ~ package
- Multiplicity: 1, 0..1, 1..*, 0..*, m..n — how to read and write them correctly
- Relationship types (with correct UML notation for each):
  - **Association**: simple line; objects know about each other
  - **Aggregation**: hollow diamond; "has a" but part can exist without whole (Department ◇—Employee)
  - **Composition**: filled diamond; "has a" and part cannot exist without whole (House ◆—Room)
  - **Inheritance/Generalisation**: hollow triangle arrow; "is a" (Dog △—Animal)
  - **Dependency**: dashed arrow; one class uses another temporarily
  - **Realisation**: dashed hollow triangle arrow; class implements an interface
- **The aggregation vs composition trap**: in composition, deleting the whole deletes the parts; in aggregation, parts survive
- Drawing exercise: Library Management System class diagram

## 5.4 — Data Flow Diagrams (DFD) [STRUCTURED ANALYSIS]
- DFD is from structured analysis (pre-UML), not UML — but still widely taught and examined
- The four Yourdon-DeMarco symbols: Process (circle/bubble), External Entity (rectangle), Data Store (open rectangle), Data Flow (arrow)
- Level 0 — Context Diagram: the entire system as one bubble; shows only external entities and data flows in/out
- Level 1: expand the system bubble into its major sub-processes; same external entities appear at edges
- Level 2: expand a specific Level 1 process into its sub-processes
- **Balancing rule**: any data flow entering or leaving a process at Level N must also appear at Level N+1 when that process is expanded — this is what "balancing" means
- DFD rules: processes must have at least one input and one output; data cannot flow directly between two data stores or two external entities; data stores cannot interact directly with external entities
- Drawing exercise: Online shopping system — Level 0 then Level 1

## 5.5 — Sequence Diagrams [BEHAVIOURAL]
- Purpose: show how objects interact over time for a specific scenario
- Elements: lifelines (vertical dashed lines), activation bars (rectangles on lifelines), messages (arrows between lifelines)
- Message types: synchronous call (solid filled arrowhead), return (dashed arrow), asynchronous (half arrowhead)
- Combined fragments: alt (if-else), opt (optional), loop (repeat), par (parallel)
- Reading a sequence diagram: time flows downward; a message from A to B creates an activation bar on B
- Drawing exercise: User login sequence diagram

## 5.6 — Communication Diagrams [BEHAVIOURAL]
- Same information as sequence diagram, different layout: objects as nodes, messages as numbered arrows between them
- When to use communication vs sequence: communication emphasises relationships; sequence emphasises time ordering
- Numbering convention: 1, 1.1, 1.2, 2, 2.1 (shows nesting of calls)

## 5.7 — Activity Diagrams [BEHAVIOURAL]
- Purpose: model workflow or process flow (like a sophisticated flowchart)
- Elements: start node (filled circle), end node (filled circle in circle), action (rounded rectangle), decision (diamond), fork bar (thick horizontal bar = split parallel), join bar (thick horizontal bar = merge parallel)
- **Fork vs decision**: fork = parallel execution (both paths run); decision = branching (one path runs)
- Swimlanes: partition the diagram by actor or component; each lane's activities are that party's responsibility
- Drawing exercise: Order processing workflow with swimlanes for Customer, System, and Warehouse

## 5.8 — State Chart Diagrams [BEHAVIOURAL]
- Purpose: model the lifecycle of one object — what states it can be in and what causes transitions
- Elements: state (rounded rectangle), initial pseudostate (filled circle), final state (bullseye), transition (arrow)
- Transition syntax: `event [guard] / action` — event triggers it, guard is a condition that must be true, action executes during the transition
- Entry/exit actions: actions that run whenever you enter or exit a state
- **Statechart vs Activity**: statechart = one object's lifecycle; activity = a process or workflow involving multiple objects
- Drawing exercise: Order object statechart (Pending → Confirmed → Shipped → Delivered / Cancelled)

## 5.9 — Finite State Machines (FSMs) [FORMAL]
- Formal definition: a 5-tuple (Q, Σ, δ, q₀, F) — states, alphabet, transition function, initial state, accepting states
- Deterministic FA (DFA): for every (state, input) pair, exactly one next state
- Non-deterministic FA (NFA): for a (state, input) pair, zero or more next states are possible
- State transition table: rows = states, columns = inputs, cells = next state
- Drawing a state transition diagram from a problem description
- Why DFA is easier to implement in code: simple table lookup; NFA requires subset construction to convert
- **[NUMERICAL]**: Given a regular expression or description, draw the FSM and transition table

## 5.10 — Petri Nets [CONCURRENCY MODELLING]
- Motivation: FSMs can't easily model concurrent or distributed systems; Petri nets can
- Elements: places (circles), transitions (rectangles/bars), tokens (dots inside places), arcs (directed arrows)
- Firing rule: a transition is enabled when all its input places have at least one token; when it fires, it consumes one token from each input place and produces one token in each output place
- How Petri nets model concurrency: a fork transition produces tokens in multiple places simultaneously
- How Petri nets model conflict: two transitions share an input place; only one can fire (non-deterministic)
- Reading a Petri net execution trace
- Why Petri nets vs FSMs: Petri nets can represent parallelism compactly; FSM state space explodes

# PART 6 — Software Design: Deciding How to Build It

## 6.1 — What Design Is (And What It Isn't)
- Design is not coding. Design is the decisions made before (or during) coding that determine the code's structure
- Design levels: architectural (system structure) → interface (how components talk to each other) → component (internal design of each component) → data (how data is stored and organised)
- Design goals: correctness, efficiency, maintainability, flexibility, reusability
- Why design matters: you can't refactor your way out of a bad architecture

## 6.2 — Design Concepts
- **Abstraction**: focusing on essential characteristics, hiding irrelevant detail; procedural abstraction (functions) vs data abstraction (classes)
- **Refinement**: starting with a high-level statement and progressively adding detail
- **Modularity**: dividing software into separate units (modules) that can be developed and tested independently
- **Information Hiding**: each module hides its design decisions from other modules; the interface is all that's exposed
- **Encapsulation**: the OOP mechanism that implements information hiding — bundling data and methods, restricting direct access
- **Information hiding ≠ Encapsulation**: hiding is the principle; encapsulation is one mechanism that achieves it

## 6.3 — Coupling (How Modules Depend on Each Other) [CRITICAL]
- Definition: coupling measures the degree of interdependence between modules
- Goal: **low coupling** — changes in one module don't ripple into others
- The six types from worst (tightest coupling) to best (loosest coupling):
  1. **Content Coupling**: Module A directly modifies the internals of Module B (accessing private fields, jumping into B's code) — worst possible, never acceptable
  2. **Common Coupling**: Both A and B read/write the same global variable — change the global, both break
  3. **External Coupling**: Both A and B depend on the same external format, protocol, or device
  4. **Control Coupling**: A passes a flag/switch to B that controls B's internal logic flow — A knows too much about B's internals
  5. **Stamp Coupling**: A passes a whole data structure to B when B only needs one field — unnecessary exposure
  6. **Data Coupling**: A passes only the specific data that B needs, nothing more — best achievable
- How to identify coupling type from a code snippet (practise this with examples)
- **Mnemonic**: Content, Common, External, Control, Stamp, Data → "Careful Coders Ensure Clean, Simple Design"

## 6.4 — Cohesion (Why Things Are Together in a Module) [CRITICAL]
- Definition: cohesion measures how strongly related and focused the responsibilities of a single module are
- Goal: **high cohesion** — every element in a module belongs there for one clear reason
- The seven types from worst (weakest cohesion) to best (strongest cohesion):
  1. **Coincidental**: elements grouped arbitrarily ("utility class" with unrelated functions) — worst
  2. **Logical**: elements perform logically similar functions (all input-handling in one module, even for unrelated inputs)
  3. **Temporal**: elements execute at the same time (initialisation routines bundled together)
  4. **Procedural**: elements follow a specific sequence of execution (step 1 then step 2 then step 3)
  5. **Communicational**: elements operate on the same data/object (everything that touches CustomerRecord)
  6. **Sequential**: output of one element is input of the next (pipeline stages)
  7. **Functional**: all elements contribute to a single, well-defined task — best possible
- How to identify cohesion type: ask "why are these things together in this module?"
- **Mnemonic**: "Confused Lazy Teenagers Prefer Communicating Sequentially, Functionally" (C, L, T, P, Comm, Seq, F)

## 6.5 — Functional Independence
- A module achieves functional independence when it has **high cohesion** and **low coupling**
- Why it matters: independently developed, independently tested, independently replaceable
- This is the design goal that coupling and cohesion are measuring toward

## 6.6 — Architectural Styles / Patterns

### 6.6.1 — Layered Architecture
- The idea: organise the system into horizontal layers; each layer provides services to the layer above and uses services from the layer below
- Strict layering: Layer N can only call Layer N-1
- Relaxed layering: layers can skip (Layer N can call Layer N-2) — better performance, worse maintainability
- Canonical example: OSI network model (7 layers); also: 3-tier web architecture (Presentation → Business Logic → Data)
- Advantages: separation of concerns, easy to replace one layer, good for incremental development
- Disadvantages: performance overhead from passing through layers, hard to cleanly separate concerns in practice
- N-tier drawing exercise: web application with browser, web server, application server, database

### 6.6.2 — Client-Server Architecture
- Client requests services; server provides them
- Thin client: most processing on server (browser is thin client to a web server)
- Thick client: significant processing on client (desktop application with local database)
- 2-tier: client talks directly to database
- 3-tier: client → application server → database (business logic separated)
- Where business logic lives in each variant — this is the exam question, not just the names

### 6.6.3 — MVC (Model-View-Controller)
- The problem it solves: UI and business logic tangled together, changing the UI breaks the logic
- Model: data and business rules; has no knowledge of the UI
- View: renders the Model for the user; multiple views can render the same model differently
- Controller: handles user input, updates the Model, selects the View
- Data flow: User input → Controller → Model (update) → View (re-render)
- Advantages: separation of concerns, independent development of UI and logic, testable Model
- Variants: MVP (Model-View-Presenter) used in Android; MVVM (Model-View-ViewModel) used in React/Angular
- Drawing the MVC data flow diagram

### 6.6.4 — Pipe and Filter Architecture
- Each filter is an independent processing component that reads input and writes output
- Pipes are the connectors that carry data between filters
- Canonical example: Unix command line (`cat file.txt | grep "error" | sort | uniq -c`)
- Each filter is stateless and independent — composability is the point
- Advantages: flexible recombination, easy to add/remove filters, parallel execution possible
- Disadvantages: not good for interactive systems, shared state across filters is hard

### 6.6.5 — Publish-Subscribe (Event-Driven) Architecture
- Publishers emit events without knowing who listens; subscribers register interest without knowing who publishes
- The broker (event bus) routes events from publishers to interested subscribers
- Advantages: full decoupling, highly scalable, easy to add new subscribers without changing publishers
- Disadvantages: hard to debug (non-linear flow), message ordering is not guaranteed, no direct feedback to publisher
- Real-world examples: Kafka, RabbitMQ, browser DOM events
- **Observer vs Pub-Sub**: Observer — Subject holds direct references to Observers (coupled); Pub-Sub — Publisher and Subscriber don't know each other (fully decoupled via broker)

## 6.7 — Design Patterns (Object-Oriented Solutions to Recurring Problems)

### 6.7.1 — What Design Patterns Are
- A pattern is a named, reusable solution to a commonly occurring design problem in a given context
- The Gang of Four (GoF) book: 23 patterns in three categories — Creational, Structural, Behavioural
- Patterns are not code — they are templates for solving problems

### 6.7.2 — Observer Pattern [BEHAVIOURAL]
- Problem: an object (Subject) needs to notify other objects (Observers) when its state changes, without being tightly coupled to them
- Solution: Subject maintains a list of Observers; when state changes, calls `notify()` on all of them
- Participants: Subject (attach, detach, notify), ConcreteSubject (state), Observer interface (update), ConcreteObserver (state sync)
- Push model: Subject sends data with the notification; Pull model: Observer fetches data from Subject after notification
- UML class diagram for Observer
- Real-world: event listeners in JavaScript, Spring ApplicationEvents

### 6.7.3 — Strategy Pattern [BEHAVIOURAL]
- Problem: multiple algorithms for the same task; want to switch algorithms at runtime without changing the client
- Solution: define a Strategy interface; each algorithm is a ConcreteStrategy that implements it; Context holds a Strategy reference and delegates to it
- UML: Context → (holds) → Strategy interface ← (implements) ConcreteStrategyA, ConcreteStrategyB
- Real-world: sorting algorithms, payment processing (CreditCard, PayPal, Crypto all implement PaymentStrategy)

### 6.7.4 — Facade Pattern [STRUCTURAL]
- Problem: a complex subsystem has many classes and a complicated interface; clients shouldn't need to know all of it
- Solution: Facade class provides a simple interface to the subsystem; clients only call the Facade
- Facade does NOT add functionality — it simplifies access to existing functionality
- Real-world: Spring's JdbcTemplate (Facade over JDBC), SLF4J (Facade over logging implementations)

### 6.7.5 — Adapter Pattern [STRUCTURAL]
- Problem: two interfaces that should work together but are incompatible
- Solution: Adapter class wraps the Adaptee (incompatible class) and presents the Target interface to the client
- Class Adapter: Adapter extends Adaptee and implements Target (uses inheritance)
- Object Adapter: Adapter holds a reference to Adaptee and implements Target (uses composition) — preferred
- Real-world: Java's InputStreamReader (adapts InputStream to Reader), database drivers

### 6.7.6 — Command Pattern [BEHAVIOURAL]
- Problem: want to decouple the sender of a request from its receiver; want undo/redo support
- Solution: encapsulate a request as an object (Command) with an execute() method; the Invoker calls execute() without knowing what it does; the Receiver does the actual work
- UML: Client → Invoker (holds Command) → Command interface (execute()) ← ConcreteCommand (holds Receiver)
- Real-world: GUI button actions, transaction rollback

### 6.7.7 — Proxy Pattern [STRUCTURAL]
- Problem: need to control access to an object (for security, performance, or because the object is remote)
- Types: Virtual Proxy (lazy loading), Remote Proxy (local stand-in for remote object), Protection Proxy (access control)
- Real-world: Spring's `@Transactional` (creates a proxy that wraps methods with transaction management)

# PART 7 — Software Testing: Proving It Works

## 7.1 — Testing Fundamentals
- Testing vs debugging: testing finds *that* a defect exists; debugging finds *where* it is — these are different activities
- Verification vs validation: verification — are we building the product right? Validation — are we building the right product?
- Error vs Fault vs Failure: Error (human mistake) → Fault/Defect (in the code) → Failure (observable wrong behaviour at runtime)
- The testing oracle problem: how do you know what the correct output should be?
- Why you can't test everything: complete testing requires testing infinite inputs; that's why we use coverage criteria

## 7.2 — Black Box Testing — Equivalence Partitioning [NUMERICAL]
- Black box = test without knowing internal code; test based on specification/requirements only
- Equivalence Partitioning: divide the input domain into classes where all values in a class are assumed to produce the same type of result
- Valid equivalence classes: inputs that should be accepted and processed normally
- Invalid equivalence classes: inputs that should be rejected
- Rule: pick one representative value per class — you don't need to test every value in a class
- How to identify classes from a spec: look for ranges, sets, boolean conditions, collections
- **[NUMERICAL]**: Given a spec "age must be between 1 and 120", identify valid and invalid classes and pick test cases

## 7.3 — Black Box Testing — Boundary Value Analysis [NUMERICAL]
- BVA targets values at the edges of equivalence classes, because programmers most often make off-by-one errors there
- For a range [a, b], the BVA test points are: a-1, a, a+1, b-1, b, b+1 (six points per boundary)
- BVA is not a replacement for EP — they complement each other: EP identifies the classes, BVA selects values at the boundaries of those classes
- **[NUMERICAL]**: For age [1, 120], list all BVA test points and categorise each as valid or invalid
- Two-variable BVA: when input has two variables, generate combinations of boundary values (can explode to many test cases)

## 7.4 — White Box Testing — Control Flow Graph (CFG) [NUMERICAL]
- White box = test with full knowledge of the source code; test the structure, not just the specification
- How to convert code to a CFG:
  - Each sequential statement = one node
  - Each branch (if/else, switch case) = one node with multiple outgoing edges
  - Each loop condition = one node with two outgoing edges (loop body, loop exit)
  - All paths must eventually reach the exit node
- Node types: process node (sequential statements), decision/predicate node (branch)
- Back edges indicate loops
- **[NUMERICAL]**: Given a 15-line function with one if-else and one while loop, draw the CFG

## 7.5 — White Box Testing — Cyclomatic Complexity [NUMERICAL]
- Cyclomatic Complexity V(G): a quantitative measure of the logical complexity of a program; also = the minimum number of independent test paths needed
- Three equivalent formulas:
  - V(G) = E − N + 2P (edges minus nodes plus 2 times connected components; P=1 for a single function)
  - V(G) = number of regions in the planar graph (count the enclosed areas including the outer region)
  - V(G) = number of predicate nodes (decision points) + 1
- **The third formula is fastest**: count all if, while, for, case, and/&&, or/|| in the code; add 1
- **[NUMERICAL]**: Given a CFG with E=10, N=8, P=1 → V(G) = 10 − 8 + 2 = 4; list 4 independent paths

## 7.6 — Coverage Criteria [HIERARCHY]
- **Statement Coverage**: every statement executed at least once; weakest criterion; easy to achieve
- **Branch Coverage**: every branch (both true and false) of every decision executed at least once; subsumes statement coverage
- **Condition Coverage**: every individual condition in a compound predicate takes both true and false; doesn't subsume branch coverage
- **Path Coverage**: every possible path through the program executed; theoretically complete, practically impossible for loops
- Hierarchy: path ⊇ branch ⊇ statement
- **Exam trap**: 100% branch coverage does NOT guarantee 100% path coverage (paths = combinations of branches)

## 7.7 — Unit Testing
- Scope: testing a single module (function, class, method) in isolation
- Test harness: the infrastructure needed to run tests (test framework, setup/teardown)
- **Stub**: a dummy implementation of a module that is called by the module under test but not yet implemented; simulates the callee
- **Driver**: a dummy caller that invokes the module under test and provides test inputs; simulates the caller
- Why stubs and drivers: to isolate the module under test from its dependencies
- Modern unit testing: JUnit (Java), pytest (Python), jest (JavaScript); mocking frameworks simulate dependencies

## 7.8 — Integration Testing
- Scope: testing interactions between modules; finding interface defects
- Why it's separate from unit testing: modules work correctly in isolation but break when connected
- **Big Bang Integration**: integrate all modules at once and test; fast to set up but debugging is a nightmare — don't do this
- **Top-Down Integration**: start from the top-level modules; use stubs for unimplemented lower modules; progressively replace stubs with real code; pros: high-level logic tested early; cons: need many stubs
- **Bottom-Up Integration**: start from the lowest-level modules; use drivers for unimplemented upper modules; pros: no stubs needed; cons: top-level system not visible until late; needs drivers
- **Sandwich (Hybrid)**: top-down for upper layers, bottom-up for lower layers simultaneously
- Which needs stubs and which needs drivers — key exam question

## 7.9 — System Testing
- Scope: testing the entire system against the system requirements
- Functional testing: does the system do what the SRS says?
- Performance testing: response time, throughput under expected load
- Stress testing: push beyond normal operating limits until it breaks; find the breaking point
- Volume testing: large amounts of data
- Security testing: vulnerability scanning, penetration testing basics
- Acceptance Testing: User Acceptance Testing (UAT) — customer validates the system
  - Alpha testing: internal users at development site
  - Beta testing: external users at customer site

## 7.10 — Regression Testing
- Not a type of testing — it's a policy of *when* to test
- After any change (bug fix, new feature, refactor): rerun all existing tests to ensure nothing that worked before now breaks
- The automation dependency: manual regression testing on a large system is impractical; CI pipelines automate this

## 7.11 — Debugging Strategies
- Brute force: add print statements everywhere; inefficient but sometimes necessary
- Backtracking: start from the failure and trace backward through the code to find the fault
- Cause elimination: form hypotheses about the cause; design tests to eliminate or confirm each hypothesis
- Rubber duck debugging: explain the code line by line (to a person or object); the explanation often reveals the bug

## 7.12 — Program Analysis
- **Static Analysis**: analyse source code or bytecode without executing it; find potential defects at compile time
  - Examples: linting (style), data flow analysis (use before initialise), control flow analysis, type checking
  - Tools: FindBugs, SonarQube, ESLint, mypy
- **Dynamic Analysis**: analyse the program during execution
  - Examples: code coverage measurement, memory leak detection, profiling (where is time spent)
  - Tools: JaCoCo (coverage), Valgrind (memory), VisualVM (profiling)

## 7.13 — Symbolic Execution
- Instead of running with concrete values (x=5), run with symbolic values (x=sym)
- Accumulate path conditions: at each branch, add the branch condition to the path condition for that path
- A test case = an assignment of concrete values that satisfies the path condition
- Advantage: can automatically generate test inputs that cover all paths
- Limitations: path explosion for loops, SMT solver (constraint solving) is expensive
- Tools: KLEE, Z3

## 7.14 — Model Checking
- Verify that a system model satisfies a property, by exhaustive state space exploration
- Properties expressed in temporal logic: CTL or LTL
  - Safety property: "bad thing never happens" (the system never deadlocks)
  - Liveness property: "good thing eventually happens" (every request eventually gets a response)
- Counterexample: if a property is violated, the model checker produces an execution trace showing the violation
- Limitation: state space explosion for large systems
- Tools: SPIN (for concurrent systems), NuSMV (for hardware/embedded)

# PART 8 — Project Management: Making It Happen on Time and Budget

## 8.1 — What Software Project Management Is
- Planning: what will be built, by whom, with what resources, by when
- Estimation: how long will it take, how much will it cost (and why estimates are almost always wrong)
- Scheduling: allocating tasks to people and time
- Risk management: identifying what could go wrong and preparing responses
- The iron triangle: scope, time, cost — you can only control two

## 8.2 — Effort Estimation — COCOMO [NUMERICAL]
- COCOMO (Constructive Cost Model) estimates effort from Lines of Code
- Basic COCOMO: E = a × KDLOC^b (E in person-months; KDLOC = thousands of lines of code)
- Duration: D = c × E^d (D in calendar months)
- Team size: P = E / D (people)
- Three modes (each has different a, b, c, d constants):
  - **Organic**: small team, familiar domain, small project (a=2.4, b=1.05, c=2.5, d=0.38)
  - **Semi-detached**: medium team, mixed experience, medium project (a=3.0, b=1.12, c=2.5, d=0.35)
  - **Embedded**: large team, constrained requirements, complex project (a=3.6, b=1.20, c=2.5, d=0.32)
- **[NUMERICAL]**: Given a 50 KDLOC semi-detached project, compute E, D, P

## 8.3 — Effort Estimation — Function Point Analysis
- FPA estimates size independent of programming language (unlike COCOMO which needs SLOC)
- Count five types of components, each weighted by complexity (simple/medium/complex):
  1. External Inputs (EI): data entering the system
  2. External Outputs (EO): data leaving the system
  3. External Inquiries (EQ): query-response pairs
  4. Internal Logical Files (ILF): logical data maintained by the system
  5. External Interface Files (EIF): logical data maintained by other systems but used by this one
- Total Unadjusted Function Points (UFP) = sum of all weighted counts
- Adjusted FP = UFP × (0.65 + 0.01 × sum of 14 General System Characteristics)
- Why FP matters: language-independent; estimated early from requirements; convert to SLOC using language factor tables

## 8.4 — Project Scheduling — CPM and PERT [NUMERICAL]
- Why scheduling matters: dependencies between tasks mean you can't do everything in parallel
- **Network diagram**: nodes represent activities (AON: Activity on Node) or events; arrows represent dependencies
- **Critical Path Method (CPM)**:
  - Forward pass: for each activity, compute Earliest Start Time (EST) and Earliest Finish Time (EFT)
    - EST = max(EFT of all predecessors); EFT = EST + duration
  - Backward pass: for each activity, compute Latest Finish Time (LFT) and Latest Start Time (LST)
    - LFT = min(LST of all successors); LST = LFT − duration
  - Float (Slack) = LST − EST = LFT − EFT
  - Critical Path: the path through the network where every activity has Float = 0; this is the minimum project duration; any delay on the critical path delays the entire project
- **PERT (Programme Evaluation and Review Technique)**:
  - Handles uncertainty by using three time estimates per activity
  - Optimistic (a), Most Likely (m), Pessimistic (b)
  - Expected time (te) = (a + 4m + b) / 6
  - Variance (σ²) = ((b − a) / 6)²
  - After computing te for each activity, apply CPM normally
- **[NUMERICAL]**: Given a table of activities with durations and dependencies, draw the network, compute forward and backward passes, identify the critical path, compute float for each activity

## 8.5 — Risk Management
- Risk: a problem that might occur; characterized by probability and impact
- Risk identification: brainstorming, checklists, historical data
- Risk analysis: probability × impact = risk exposure
- Risk planning: avoidance (eliminate the risk), mitigation (reduce probability or impact), contingency (plan what to do if it occurs), acceptance (tolerate it)
- Risk monitoring: track identified risks; watch for new risks

## 8.6 — Software Configuration Management (SCM)
- The problem: multiple developers, multiple versions, multiple environments — how do you keep track of what was built and when?
- **Configuration Item (CI)**: any artifact that is subject to change control (source files, build scripts, test cases, documentation, database schemas)
- **Baseline**: a snapshot of one or more CIs at a defined point, formally approved and placed under change control
- **Version Control**: tracking changes to CIs over time; Git is the universal tool today
  - Concepts: commit, branch, merge, tag, conflict resolution
- **Change Control**: formal process for requesting, evaluating, approving, and implementing changes to baselined CIs
- **SCM activities**: Identification → Version Control → Change Control → Status Accounting → Auditing

## 8.7 — DevOps: The Paradigm

### 8.7.1 — What DevOps Is and Why It Exists
- The "wall of confusion": Development wants to ship new features fast; Operations wants stability; these goals conflict
- DevOps: cultural and technical movement to break down the Dev/Ops wall; shared responsibility for the full software lifecycle
- CALMS framework: Culture, Automation, Lean, Measurement, Sharing
- The DevOps infinity loop: Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → (back to Plan)

### 8.7.2 — The CI/CD Pipeline [DEPLOYMENT PIPELINE]
- **Continuous Integration (CI)**: every commit triggers an automated build and test suite; goal: find integration problems within minutes, not weeks
  - Stages: Source Control → Build → Unit Tests → Code Analysis
- **Continuous Delivery (CD)**: the pipeline automatically prepares a release artifact ready for deployment; deployment still requires human approval
- **Continuous Deployment**: the pipeline automatically deploys to production without human approval; requires very high test confidence
- Pipeline stages in order: Commit → Build → Unit Test → Integration Test → Acceptance Test → Performance Test → Staging Deploy → Production Deploy
- **Test pyramid**: many unit tests (fast, cheap), fewer integration tests, even fewer end-to-end tests (slow, expensive, fragile)

### 8.7.3 — Deployment Strategies
- **Blue-Green Deployment**: maintain two identical production environments (Blue = current, Green = new); deploy to Green, test Green, then switch traffic from Blue to Green; instant rollback by switching back; requires double infrastructure
- **Canary Deployment**: route a small percentage of traffic (1-5%) to the new version; monitor error rates and performance; gradually increase percentage or rollback; named after the canary in a coal mine
- **Rolling Deployment**: replace instances of the old version one at a time with the new version; slower but uses existing infrastructure

### 8.7.4 — Infrastructure and Operations
- **Infrastructure as Code (IaC)**: manage infrastructure (servers, networks, databases) using code and version control; tools: Terraform (provision), Ansible (configure)
- **Containers and Orchestration**: Docker packages an application and its dependencies into a portable unit; Kubernetes orchestrates many containers across many machines
- **The Three Pillars of Observability**: Logs (what happened), Metrics (numeric measurements over time), Traces (how a request moved through the system)
- **SLI/SLO/SLA**:
  - SLI (Service Level Indicator): a measured metric (e.g., latency at 99th percentile)
  - SLO (Service Level Objective): the target for that metric (e.g., p99 latency < 200ms)
  - SLA (Service Level Agreement): contractual commitment; penalty if SLO is breached

### 8.7.5 — Cloud Platforms
- IaaS (Infrastructure as a Service): you manage OS and up; provider manages hardware and hypervisor; example: EC2
- PaaS (Platform as a Service): you manage application and data; provider manages everything else; example: Heroku, Google App Engine
- SaaS (Software as a Service): you just use the application; provider manages everything; example: Gmail, Salesforce
- Cloud-native: applications designed to exploit cloud characteristics — elasticity (auto-scale), distributed, resilient, managed services

### 8.7.6 — DevOps Tools Overview
- CI/CD runners: Jenkins, GitHub Actions, GitLab CI
- Containerisation: Docker
- Orchestration: Kubernetes
- IaC provisioning: Terraform
- IaC configuration: Ansible
- Monitoring: Prometheus (metrics collection), Grafana (visualisation)
- Know which category each belongs to — not just the names
