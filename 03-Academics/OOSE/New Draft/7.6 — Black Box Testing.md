# 7.6 — Black Box Testing

Black Box Testing:
> tests software functionality without knowing internal implementation.

Focus:
- inputs
- outputs
- expected behaviour

Internal code remains hidden.

---

# Example

```text
Input:
username = admin
password = 1234

Expected:
login success
```

Tester does not care about:
- algorithms
- database queries
- source code

---

# Characteristics

| Characteristic | Meaning |
|---|---|
| No code knowledge required | Internal logic hidden |
| Behaviour-focused | Tests functionality |
| Input/output based | Compare expected vs actual |
| User perspective | External behaviour testing |

---

# Common Techniques

- Equivalence Partitioning
- Boundary Value Analysis
- Decision Table Testing
- State Transition Testing

---

# Equivalence Partitioning

Divide inputs into groups.

Example:

```text
Password length:
8–16 valid
```

Partitions:

```text
<8
8–16
>16
```

Test one value from each group.

---

# Boundary Value Analysis

Tests edge values.

Example:

```text
Valid range:
1–100
```

Test:

```text
0
1
100
101
```

---

# Decision Table Testing

Used for multiple condition combinations.

Example:

```text
Valid Card?
Sufficient Balance?
```

---

# State Transition Testing

Tests behaviour during state changes.

Examples:
- login attempts
- ATM states
- order states

---

# Black Box vs White Box

| Black Box | White Box |
|---|---|
| Internal code hidden | Internal logic visible |
| Behaviour-focused | Code/path-focused |
| User perspective | Developer perspective |

---

# Advantages

- independent of implementation
- validates user behaviour
- useful for requirement testing

---

# Disadvantages

- internal code coverage unknown
- may miss hidden logic/path errors

---

# Important Insight

Black Box Testing verifies:
> external behaviour of software

without considering internal implementation
