# 6.1 — Design Concepts Overview

Design phase answers:
> how the system should be internally organized.

Requirements define:
- what system should do

Design defines:
- structure
- modules
- relationships
- architecture

---

# Main Design Goals

| Goal | Meaning |
|---|---|
| Modularity | Divide system into smaller parts |
| Maintainability | Easier modification/debugging |
| Reusability | Reuse components/modules |
| Scalability | Handle future growth |
| Low Complexity | Easier understanding |

---

# Modularity

System divided into independent modules.

Example:

```text
ECommerce System
├── Auth Module
├── Payment Module
├── Order Module
└── Notification Module
```

Benefits:
- easier maintenance
- parallel development
- reduced complexity

---

# Cohesion

Measures:
> how related responsibilities inside a module are.

Good design:
> High Cohesion

Example:

```text
AuthService
- login()
- logout()
- resetPassword()
```

Single focused responsibility.

---

# Coupling

Measures:
> dependency between modules.

Good design:
> Low Coupling

Example:
- PaymentService communicates through APIs/interfaces
- avoids directly modifying internal data of other modules

---

# Functional vs OO Design

| Functional Design | Object-Oriented Design |
|---|---|
| Function/process focused | Object/class focused |
| Data flow oriented | Object interaction oriented |

---

# Architectural Design

Defines:
> high-level organization of the system.

Examples:
- layered architecture
- monolith
- microservices

---

# Important Design Principles

- abstraction
- encapsulation
- separation of concerns
- information hiding

---

# Important Insight

Good design improves:
- maintainability
- readability
- scalability
- testing
- long-term development speed

Bad design causes:
- tight dependencies
- difficult maintenance
- technical debt
- difficult scaling

---

# Design Flow

```text
Requirements
→ Design
→ Implementation
```

Design acts as the bridge between:
- requirements
- actual code
