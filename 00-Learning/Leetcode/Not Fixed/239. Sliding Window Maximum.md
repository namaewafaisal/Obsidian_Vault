## LC 239. Sliding Window Maximum

| **Metric**     | **Value**                                     |
| -------------- | --------------------------------------------- |
| **Date**       | December 30, 2025                             |
| **Time Taken** | ~50 minutes                                   |
| **Difficulty** | Hard                                          |
| **Pattern**    | Sliding Window (Fixed Size) + Monotonic Deque |

---

### Problem (summary)

Given an integer array `nums` and an integer `k`, there is a **sliding window of size `k`** that moves from left to right.
For **each window position**, return the **maximum element** inside the window.

---

### Why This Is a Hard Problem

* Window size is **fixed**, but the required operation (**maximum**) is **not reversible**
* Recomputing max for each window → **O(n·k)** → TLE
* Requires discovering a **non-obvious data structure invariant**
* The optimal solution depends on **eliminating useless elements**, not storing everything

---

### Key Invariant (This Is the Entire Problem)

* The sliding window is **fixed-size** (`k`)
* The deque stores **only candidates for maximum**
* Elements in the deque are always in **monotonically decreasing order**

> **Front of deque = maximum of current window**

The deque does **not** represent the window.
It represents **future maximum candidates**.

---

### Data Structure Guide — Deque (Critical Understanding)

A `Deque` (Double-Ended Queue) allows:

| Operation                 | Meaning in This Problem                               |
| ------------------------- | ----------------------------------------------------- |
| `addLast(x)`              | Add new element entering the window                   |
| `removeLast()`            | Remove **dominated elements** (smaller than incoming) |
| `peekFirst()`             | Current window maximum                                |
| `pop()` / `removeFirst()` | Remove expired element when window moves              |

Two **independent removal reasons** exist:

1. **Dominance removal** (value-based)
2. **Window expiry** (index / time-based)

Mixing these is the most common mistake.

---

### Thinking Log (Evolution of the Solution)

#### Initial Observation

* Window size is fixed → sliding window
* Need max efficiently → brute force impossible

---

#### First Incorrect Instinct

* Track a running max
* But when max leaves the window, we don’t know the next max

→ **State loss**

---

#### Second Attempt

* Use a normal queue
* But queues don’t allow removing useless elements

→ Still too slow or incorrect

---

#### Key Realization

> **Many elements in the window can never become the maximum again**

If a larger element appears **to the right**, all smaller elements **to its left** are permanently useless.

They must be removed **immediately**, even if still inside the window.

---

#### The Breakthrough

Instead of storing the entire window:

> Store only elements that can still become the maximum in the future

This leads directly to a **monotonic deque**.

---

### Monotonic Deque Invariant

At all times:

```
queue[0] ≥ queue[1] ≥ queue[2] ≥ ...
```

* Front → largest
* Back → smallest
* Size ≤ k (often much smaller)

---

### Sliding Window Mechanics (Exact Logic)

#### When adding a new element (`right` moves)

1. Remove elements from **back** while they are smaller than `nums[right]`

   * They are **dominated**
   * They can never be max again
2. Add `nums[right]` to the back

---

#### When window exceeds size `k`

1. If the outgoing element (`nums[left]`) equals the **front**

   * Remove it from front
2. Increment `left`

---

#### When window size equals `k`

* The front of deque is the maximum
* Add it to the result

---

### Why This Works (Core Insight)

Each element:

* Is added **once**
* Is removed **once**

Total operations → **O(n)**

The deque continuously maintains a **compressed representation** of the window’s maximum logic.

---

### Implementation Strategy

1. Initialize pointers `left = 0`, `right = 0`
2. Use a `Deque<Integer>` to store **values** in decreasing order
3. For each `right`:

   * Remove dominated elements from the back
   * Add current value
4. If window size exceeds `k`, shrink from left:

   * Remove front if it equals outgoing value
5. If window size is exactly `k`, record front as max

---

### Final Code (Java)

```java
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        int left = 0;
        int right = 0;
        int[] result = new int[nums.length - k + 1];
        int index = 0;

        Deque<Integer> queue = new ArrayDeque<>();

        while (right < nums.length) {

            // Remove dominated elements
            while (!queue.isEmpty() && queue.peekLast() < nums[right]) {
                queue.removeLast();
            }

            queue.addLast(nums[right]);

            // Maintain fixed window size
            while (right - left + 1 > k) {
                if (queue.peekFirst().equals(nums[left])) {
                    queue.pop();
                }
                left++;
            }

            // Record result when window is valid
            if (right - left + 1 == k) {
                result[index++] = queue.peekFirst();
            }

            right++;
        }
        return result;
    }
}
```

### Complexity Analysis

| Metric    | Complexity | Reason                              |
| --------- | ---------- | ----------------------------------- |
| **Time**  | O(n)       | Each element added and removed once |
| **Space** | O(k)       | Deque stores only candidates        |

---

### Mental Model (One-Line Rule)

> **Store only future maximum candidates in a decreasing deque; front is always the answer.**
