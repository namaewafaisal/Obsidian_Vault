## LC 31. Next Permutation

### Problem (Statement)

Given an integer array `nums` representing a permutation, rearrange it into the **next lexicographically greater permutation**.

If such arrangement is not possible, rearrange it into the **lowest possible order** (ascending).

Constraints:
- Must modify the array **in-place**
- Use only **constant extra space**

---

### Key Observation

> The next permutation is obtained by making the **smallest possible increase** from the rightmost side.

This means:
- Changes should happen as far **to the right** as possible
- The increase should be **minimal**, not arbitrary

---

### Core Idea (Lexicographic Invariant)

> Everything to the right of the pivot is already the **largest possible arrangement** for that prefix.

So:
- We must change the **pivot**
- Then reset the suffix to its **smallest form**

This splits the problem into:
1. Increasing the number minimally
2. Making the remainder as small as possible

---

### Thinking Log (Mandatory)

#### My initial thinking (your words)

> After swapping, sometimes the array already becomes the next permutation,  
> so reversing the suffix feels unnecessary or even wrong.

> I thought I should reverse only if the suffix is not already ascending.

---

#### Why this thinking breaks (correction)

- The algorithm is built on **guarantees**, not coincidences
- Sometimes the suffix *happens* to already be minimal
- But in general, after swapping, the suffix is **still not guaranteed minimal**

Skipping reversal relies on **special cases**, not invariants.

---

#### Corrected mental model

> Swapping makes the permutation larger.  
> Reversing the suffix makes it the **next** one.

Both steps are mandatory.

---

### Pivot Logic (Critical Step)

Scan from right → left and find the first index `i` such that:
```
nums[i] < nums[i + 1]
```

This index is the **pivot**.

Meaning:
- Suffix to the right of `i` is **non-increasing**
- No rearrangement inside the suffix alone can create a larger permutation

---

### Swap Logic (Minimal Increase)

After finding the pivot:
- Search **from the end of the array toward the pivot**
- Find the **first element greater than `nums[pivot]`**
- Swap it with the pivot

Why from the end?
- Because the suffix is non-increasing
- The first valid element from the right is the **smallest greater one**

---

### Suffix Reversal (Always Required)

After the swap:
- The suffix is still in its **largest arrangement**
- To minimize the increase, it must be reversed

Rule:
> **Always reverse everything to the right of the pivot.**

If the suffix is already ascending, reversal becomes a no-op — which is fine.

---

### Algorithm Overview

1. Find the pivot (rightmost increasing pair)
2. If no pivot exists → reverse entire array
3. Swap pivot with smallest greater element from the right
4. Reverse the suffix (pivot + 1 → end)

Time: `O(n)`  
Space: `O(1)`

---

### Final Code (Java)

```java
class Solution {
    public void nextPermutation(int[] nums) {
        int n = nums.length;
        int pivot = -1;

        // Step 1: find pivot
        for (int i = n - 2; i >= 0; i--) {
            if (nums[i] < nums[i + 1]) {
                pivot = i;
                break;
            }
        }

        // Step 2: if no pivot, reverse whole array
        if (pivot == -1) {
            reverse(nums, 0, n - 1);
            return;
        }

        // Step 3: swap with smallest greater element on right
        for (int i = n - 1; i > pivot; i--) {
            if (nums[i] > nums[pivot]) {
                swap(nums, i, pivot);
                break;
            }
        }

        // Step 4: reverse suffix
        reverse(nums, pivot + 1, n - 1);
    }

    private void reverse(int[] nums, int left, int right) {
        while (left < right) {
            swap(nums, left++, right--);
        }
    }

    private void swap(int[] nums, int i, int j) {
        int temp = nums[i];
        nums[i] = nums[j];
        nums[j] = temp;
    }
}
```

### Common Mistakes

- Searching for swap candidate from left → right
- Skipping suffix reversal conditionally
- Treating this as a sorting problem
- Thinking reversal is an optimization instead of an invariant
- Forgetting lexicographic ordering rules
