## Trees — Core Recursion & Traversal Concepts

### What this note is

This is a **concept foundation note** created while learning **LC 226 (Invert Binary Tree)**.  
The goal is to lock in **how trees work**, **how recursion works on trees**, and **where my initial thinking was wrong**.

This note is meant to be recalled **before solving tree problems**, not after.

---

## Problem Context (Anchor)

Most introductory tree problems (like LC 226) give:

```java
public TreeNode invertTree(TreeNode root)
```

Even though LeetCode shows input as an **array**, the actual input is:
- a **TreeNode reference**
- with `left` and `right` pointers

The array is only a **visual representation**.

---

## Key Invariant (Most Important)

> **Tree recursion works through in-place mutation of node links, not through returned values.**

- Nodes do not move
- Values do not move
- **Only references (left / right pointers) change**

---

## Thinking Log (Actual Thought Process + Corrections)

### Initial Thought

> *“I need to go deep first, so I probably need BFS or some layer-based logic.”*

**Why this was wrong**
- “Going deep” implies **DFS**, not BFS
- BFS is level-by-level, not depth-first
- Tree inversion does not depend on levels

---

### Confusion About DFS

> *“In DFS we go to the bottom and when returning we do the operation.”*

**Correction**
- DFS only defines **visit order**
- **Operation timing is my choice**
- Preorder, inorder, postorder are all DFS

DFS ≠ bottom-up by default.

---

### Confusion About `return root`

> *“The recursive calls don’t really need the return, only the outer method does.”*

**Correct Understanding**
- The recursion works via **side effects**
- Swapping `left` and `right` mutates the tree directly
- Recursive calls ignore the return value
- `return root` exists only to satisfy the method contract for the caller

---

### Overengineering the Structure

> *“I thought I needed another helper function just for recursion.”*

**Why this was unnecessary**
- The function itself **is the recursive function**
- No extra state is needed
- No aggregation of results is needed

One function is enough.

---

### Visualization Issue (Root Cause)

> *“Swapping is easy, but visualizing what happens was hard.”*

**Breakthrough**
- I am not moving nodes
- I am **flipping arrows**
- Every node does the same local operation

Once I saw recursion as **applying a rule everywhere**, not “controlling flow”, it clicked.

---

## Correct Mental Model (Locked)

### How to approach any tree problem

1. Define **what should happen at one node**
2. Apply that logic locally
3. Recursively apply the same logic to subtrees
4. Let recursion handle traversal

You do **not** manage depth or order manually.

---

## DFS vs BFS (Clarified)

### DFS
- Go deep first
- Natural fit for recursion
- Operation timing is flexible (pre / in / post)

### BFS
- Level by level
- Uses a queue
- Operation always happens top-down

### Correct rule

| Problem depends on | Use |
|------------------|-----|
| Subtrees | DFS |
| Children results | DFS (postorder) |
| Parent state | DFS (preorder) |
| Levels / distance | BFS |

## Example Anchor Code (Invert Tree)

```java
class Solution {
    public TreeNode invertTree(TreeNode root) {
        if (root == null) return null;

        TreeNode temp = root.left;
        root.left = root.right;
        root.right = temp;

        invertTree(root.left);
        invertTree(root.right);

        return root;
    }
}
```

**Why this works**
- The tree is mutated in place
- Recursion ensures every node is visited
- Return value is only for the top-level caller

---

## Common Beginner Mistakes (Now Avoided)

- Thinking trees are index-based like arrays
- Mixing traversal order with operation timing
- Assuming recursion needs helper functions
- Assuming DFS means bottom-up logic
- Overthinking `return` values instead of side effects

---

## One-Sentence Recall

> Tree recursion works by applying the same local rule at every node through pointer mutation; traversal order and return values are secondary.
