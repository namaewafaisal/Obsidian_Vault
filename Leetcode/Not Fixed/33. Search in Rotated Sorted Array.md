## LC 33. Search in Rotated Sorted Array

### Problem (Statement)

You are given an integer array `nums` that was originally sorted in ascending order
but then **rotated at an unknown pivot**.

Given an integer `target`, return its **index** if it exists in the array,
otherwise return `-1`.

Constraints:
- Exactly one rotation
- All elements are **distinct**
- Required time complexity: `O(log n)`

---

### Input / Output

**Input**
```
nums = [4,5,6,7,0,1,2]
target = 0
```

**Output**
```
4
````

---

### Key Invariant

> **At every step of binary search, at least one half of the array is sorted.**

Binary search still works because we can **identify the sorted half and discard the other**.

---

### Thinking Log (Actual Evolution, Mistakes Included)

#### ❌ Initial Wrong Idea — Rebuilding / Deque

> *“Use a deque, add elements, detect the rotation point, reverse parts.”*

Why this was wrong:
- Linear traversal
- Rearranging elements
- Might already pass the target
- Violates `O(log n)`

**Correction:**  
Rebuilding the array destroys the problem structure.

---

#### ✅ Second Idea — Find Pivot First

> *“Find the rotated index using binary search, then search in the two sorted halves.”*

This works:
- `O(log n)` pivot search
- `O(log n)` target search

But it’s **not optimal**.

---

#### 🔑 Key Realization

> *“I can merge pivot finding and target search in a single loop.”*

This is the **intended solution**.

Binary search logic + rotation awareness in **one loop**.

---

#### ❌ Mistake #1 — Comparing with `nums[0]` or `nums[n-1]`

> *“If mid > nums[0] then I’m in left half; if mid < nums[n-1] then right half.”*

Why this is wrong:
- Binary search **shrinks the range**
- `low` is no longer `0`
- `high` is no longer `n-1`
- Comparisons must be **local**, not global

**Correction:**  
Always compare using `low`, `mid`, `high`.

---

#### ❌ Mistake #2 — Using `<` instead of `<=`

Buggy condition:
```java
nums[low] < nums[mid]
````

This failed for:

```
nums = [3,1], target = 1
```

Why:

* When `low == mid`, `<` is false
* A single-element half is still sorted
* Wrong half gets discarded

**Correction:**

```java
nums[low] <= nums[mid]
```

This correctly handles **single-element halves**.

---

#### ❌ Mistake #3 — Excluding `mid` incorrectly

> *“Maybe mid should not be included.”*

Why this is wrong:

* `mid` belongs to one of the halves
* Excluding it breaks boundary logic
* Can skip valid answers

**Correction:**
Always include `mid` in the sorted-half check.

---

#### ✅ Alternative That Also Works (Clarified)

You asked:

> *“What if I use `nums[mid] <= nums[high]`?”*

Answer:

* Yes, it works
* It detects the **right sorted half**
* Logic must flip accordingly

This is **equivalent**, but must be used consistently.

---

### Correct Mental Model (Final)

At each iteration:

1. Check `nums[mid] == target`
2. Determine which half is sorted:

   * Left sorted if `nums[low] <= nums[mid]`
   * Else right sorted
3. Check if `target` lies **within the sorted half**
4. Discard the other half

This preserves the binary search invariant:

> **Each iteration removes half the search space.**

---

### Final Correct Code (Java)

```java
class Solution {
    public int search(int[] nums, int target) {
        int low = 0, high = nums.length - 1;

        while (low <= high) {
            int mid = low + (high - low) / 2;

            if (nums[mid] == target) {
                return mid;
            }

            // Left half is sorted
            if (nums[low] <= nums[mid]) {
                if (target >= nums[low] && target < nums[mid]) {
                    high = mid - 1;
                } else {
                    low = mid + 1;
                }
            }
            // Right half is sorted
            else {
                if (target > nums[mid] && target <= nums[high]) {
                    low = mid + 1;
                } else {
                    high = mid - 1;
                }
            }
        }
        return -1;
    }
}
```

---

### Complexity Analysis

* **Time:** `O(log n)`
* **Space:** `O(1)`

---

### Final Lock-In Rules

* Always reason **locally** (`low`, `mid`, `high`)
* Always include `mid`
* Always use `<=` for sorted-half detection
* One half is **guaranteed sorted** — find it

---

### One-Sentence Recall

> Rotated binary search works because even after rotation, one half is always sorted — you just need to detect it correctly.
