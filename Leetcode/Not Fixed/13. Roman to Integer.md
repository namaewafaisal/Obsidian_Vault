## Problem (Statement)

Given a Roman numeral string `s`, convert it into its corresponding integer value.

Roman numerals are written using the following symbols:

| Symbol | Value |
| ------ | ----- |
| I      | 1     |
| V      | 5     |
| X      | 10    |
| L      | 50    |
| C      | 100   |
| D      | 500   |
| M      | 1000  |

### Subtractive Rule

If a smaller value appears **before** a larger value, it is subtracted.

---

## Input / Output

**Input:**
`s = "MCMIV"`

**Output:**
`1904`

---

## Pattern Classification

* String traversal
* Greedy local decision
* Neighbor comparison
* Parsing with rules

---

## Core Rule (Invariant)

At index `i`:

```
If value(s[i]) < value(s[i+1]) → subtract
Else → add
```

Decision is **local**, not global.

---

## Initial Thinking (My Approach)

* Roman numerals sometimes work in **pairs** (IV, IX, CM, etc.)
* So compare current and next characters
* If next is bigger → handle both together
* Else → add current

This led to:

* Pair handling
* Index jumping (`i += 2`)
* End-of-string special case

---

## My Original Code (Working)

```java
class Solution {
    public int romanToInt(String s) {
        Map<Character, Integer> map = new HashMap<>();
        map.put('I',1);
        map.put('V',5);
        map.put('X',10);
        map.put('L',50);
        map.put('C',100);
        map.put('D',500);
        map.put('M',1000);

        int result = 0;
        int i = 0;

        while (i < s.length() - 1) {
            char cr = s.charAt(i);
            char nx = s.charAt(i + 1);
            int cv = map.get(cr);
            int nv = map.get(nx);

            if (nv > cv) {
                result += nv - cv;
                i += 2;
            } else {
                result += cv;
                i++;
            }
        }

        if (i == s.length() - 1) {
            result += map.get(s.charAt(i));
        }

        return result;
    }
}
```

---

## What Worked Well

* Correct understanding of subtractive cases
* No hard-coded pairs (`IV`, `IX`, etc.)
* Optimal time and space
* Correct for all valid inputs

---

## Where It Was Overcomplicated

* Pair consumption (`i += 2`)
* Loop stopping at `length - 1`
* Extra check for last character

These add **index bookkeeping**, not logical correctness.

---

## Key Insight (Improved Thinking)

Subtractive notation does **not require pairing**.

Instead:

* Treat each symbol independently
* If it should be subtracted → subtract its value
* Let the next iteration add the larger value naturally

This keeps:

* Same logic
* Fewer moving parts

---

## Thinking Log (Evolution)

1. Roman numerals sometimes act as pairs
2. Tried consuming both characters at once
3. Logic worked but required index jumps
4. Realized subtractive logic is a **local decision**
5. Subtract current instead of combining pairs
6. Simpler traversal, same correctness

---

## Recall Notes (Read This Before Re-Solving)

* Do **not** hard-code subtractive cases
* Always compare current with next
* Subtractive case = current contributes **negative**
* Avoid index jumping unless absolutely required
* Think in **per-character contribution**
