## LC 733. Flood Fill

### Problem (Statement)

Given a 2D grid `image`, a starting cell `(sr, sc)`, and an integer `newColor`:

- Recolor the starting cell
- Recolor **all cells connected (4-directionally)** to it
- Only cells that have the **same original color** as `image[sr][sc]` should be changed

Return the modified image.

---

### Input / Output

**Input**
```
image = [
  [1, 1, 1],
  [1, 1, 0],
  [1, 0, 1]
]
sr = 1, sc = 1, newColor = 2
```

**Output**
```
[
  [2, 2, 2],
  [2, 2, 0],
  [2, 0, 1]
]
```

---

### Key Invariant

> **Flood fill is DFS on a grid where recoloring itself acts as the visited mark.**

If recoloring does not change the value, DFS will never terminate.

---

### Thinking Log (Actual Evolution, Mistakes Included)

#### Initial Intuition (Correct)

> *“This is the same as Number of Islands, but instead of erasing land, I recolor cells.”*

This mapping was correct:
- Grid = graph
- Cell = node
- 4 directions = edges

---

#### ❌ Mistake #1 — Forgetting the visited invariant

Implementation:
- DFS stopped only when `image[r][c] != originalColor`
- Visited marking was done by recoloring

Hidden issue:
- If `newColor == originalColor`, marking does **not** change state

Result:
- Same cell remains eligible for DFS
- Neighbors recurse back into it
- Infinite recursion → `StackOverflowError`

---

#### ❌ Symptom Observed

```
java.lang.StackOverflowError
  at Solution.flood
  at Solution.flood
  ...
```

This indicated:
- DFS never hit a stopping condition
- Visited state was not being invalidated

---

### Key Breakthrough

> *“DFS relies on state change to prevent revisits.”*

In LC 200:
- `'1' → '2'` ensured visited cells were skipped

In Flood Fill:
- `originalColor → newColor` must **change the value**
- Otherwise, DFS must not start

---

### Correct Mental Model (Must Lock In)

1. Save the `originalColor = image[sr][sc]`
2. If `originalColor == newColor`:
   - Do **nothing**
   - Return image immediately
3. Otherwise:
   - Run DFS
   - Recolor current cell
   - Expand to 4 neighbors
   - Stop when out of bounds or color mismatch

---

### Final Correct Code (Java)

```java
class Solution {
    int[][] image;
    int originalColor;
    int newColor;

    public int[][] floodFill(int[][] image, int sr, int sc, int newColor) {
        this.image = image;
        this.originalColor = image[sr][sc];
        this.newColor = newColor;

        if (originalColor == newColor) return image;

        dfs(sr, sc);
        return image;
    }

    private void dfs(int r, int c) {
        if (r < 0 || r >= image.length) return;
        if (c < 0 || c >= image[0].length) return;
        if (image[r][c] != originalColor) return;

        image[r][c] = newColor;

        dfs(r - 1, c);
        dfs(r + 1, c);
        dfs(r, c - 1);
        dfs(r, c + 1);
    }
}
```

---

### Why This Works

- Recoloring invalidates the DFS condition
- Each cell is visited **exactly once**
- DFS terminates naturally
- Time complexity: O(rows × cols)
- Space complexity: O(rows × cols) recursion stack (worst case)

---

### Common Mistakes (Explicit)

- Forgetting to handle `originalColor == newColor`
- Using recoloring without ensuring state change
- Letting DFS depend on a condition that never flips
- Treating flood fill as different from graph DFS

---

### One-Sentence Recall

> LC 733 works because DFS recolors each connected cell exactly once, and DFS must not start if recoloring does not change state.
