## LC 102. Binary Tree Level Order Traversal

### Problem (Statement)

Given the `root` of a **binary tree**, return the **level order traversal** of its nodes’ values.

- Nodes at the same depth must be grouped together
- Order is **top to bottom**, **left to right**
- Output shape: `List<List<Integer>>`

---

### Input / Output

**Input**
```
    3
   / \
  9  20
     / \
    15  7
```

**Output**
```
[
  [3],
  [9, 20],
  [15, 7]
]
```

---

### Key Invariant

> **At depth `d`, a node’s value belongs to bucket `d`.**

This problem is about **grouping by depth**, not traversal order.

---

### Thinking Log (Actual Evolution, Mistakes Included)

#### Initial Intuition (Correct but Misapplied)

> *“I can do this recursively if each recursion returns a list.”*

Why this felt wrong:
- Each subtree does **not** independently own a level
- Levels are a **global property**, not a subtree property
- Returning `List<List<>>` from recursion felt impossible to merge cleanly

This intuition was correct — returning lists **is wrong here**.

---

#### ❌ Mistake #1 — Trying to return lists from recursion

> *“Each recursive call can return its own `List<List>`.”*

Why this failed:
- Left and right subtrees don’t align on levels
- No clean merge logic exists
- Level information gets lost or duplicated

**Correction:**  
This problem requires **shared mutable state**, not return values.

---

#### ❌ Mistake #2 — Passing a `List<Integer>` per recursion

> *“I’ll pass a list that represents the current level.”*

Why this failed:
- One list ≠ one level across recursion
- Recursion spans multiple depths
- Impossible to know which list to reuse or create

**Correction:**  
Do **not** pass per-level lists. Pass **only depth information**.

---

#### ❌ Mistake #3 — Assuming `result[level]` already exists

> *“If I’m at level `d`, I can directly do `result[d].add()`.”*

Why this failed:
- Lists for deeper levels do not exist yet
- Accessing by index without creation breaks the invariant

**Correction:**  
Create level lists **lazily**, when first encountered.

---

### Key Breakthrough

> *“Each recursion only handles its own node and knows its depth.”*

This clarified everything:
- One recursion = one node
- One responsibility:
  - ensure bucket exists
  - put value in correct bucket
- Children handle themselves

---

### Correct Mental Model (Must Lock In)

- Use **DFS with context**
- Maintain one shared `result`
- Pass `level` down the recursion
- Never return lists from recursion
- Never think in terms of siblings or merging

---

### Final Correct Code (Java)

```java
class Solution {
    List<List<Integer>> result = new ArrayList<>();

    public List<List<Integer>> levelOrder(TreeNode root) {
        helper(root, 0);
        return result;
    }

    private void helper(TreeNode root, int level) {
        if (root == null) {
            return;
        }

        if (result.size() == level) {
            result.add(new ArrayList<>());
        }

        result.get(level).add(root.val);

        helper(root.left, level + 1);
        helper(root.right, level + 1);
    }
}
```

---

### Why This Works

- Depth (`level`) encodes grouping information
- Shared `result` preserves state across recursion
- DFS guarantees every node is visited exactly once
- Lazy list creation preserves the level invariant

---

### Common Mistakes (Explicit)

- Returning data from recursion
- Passing lists instead of depth
- Mixing child logic into parent responsibility
- Thinking traversal order defines levels

---

### One-Sentence Recall

> LC 102 works because each recursive call handles exactly one node and places its value into a shared bucket determined solely by its depth.
